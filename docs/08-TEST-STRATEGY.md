## 2. 테스트 가능 영역 분석

코드 분석 결과 다음 영역들이 테스트 대상으로 식별된다.

### 2.1 단위 테스트 대상 (순수 함수)

`src/lib/pcloud.js`에 테스트하기 좋은 순수 함수 5개가 존재한다.

#### `extractCode(url)` - 우선순위: 높음

URL 문자열에서 pCloud 공유 코드를 추출하는 함수. 3가지 정규식 패턴을 순차 매칭한다.

```javascript
// 테스트 케이스 예시
extractCode('https://e.pcloud.link/publink/show?code=ABC123')  // → 'ABC123'
extractCode('https://e.pcloud.link/publink/show?code=abc')      // → 'abc'
extractCode('https://example.com/XYZ789')                        // → 'XYZ789'
extractCode('plaincode')                                          // → 'plaincode'
```

- 각 정규식 패턴별 매칭 검증
- 매칭 실패 시 원본 URL 반환 확인
- 경계값: 빈 문자열, 특수문자 포함 URL

#### `isImageFile(filename)` - 우선순위: 높음

파일명 확장자를 기반으로 이미지 여부를 판단한다. 허용 확장자: `jpg`, `jpeg`, `png`, `gif`, `webp`, `bmp`.

```javascript
// 테스트 케이스 예시
isImageFile('page01.jpg')    // → true
isImageFile('page.PNG')      // → true (대소문자 무시)
isImageFile('comic.webp')    // → true
isImageFile('readme.txt')    // → false
isImageFile('archive.zip')   // → false
isImageFile('.jpg')          // → true (이름 없이 확장자만)
isImageFile('noext')         // → false
```

- 지원 확장자 6종 각각 검증
- 대소문자 혼합 확장자 처리 확인
- 확장자 없는 파일, 다중 점 파일명 (`image.backup.png`)

#### `naturalSort(a, b)` - 우선순위: 중간

`localeCompare`의 `numeric: true` 옵션을 사용한 자연 정렬 비교 함수.

```javascript
// 테스트 케이스 예시
const items = [{ name: 'ch10' }, { name: 'ch2' }, { name: 'ch1' }];
items.sort(naturalSort); // → [{ name: 'ch1' }, { name: 'ch2' }, { name: 'ch10' }]
```

- 숫자 포함 문자열의 자연 순서 정렬
- 한글/영문 혼합 정렬
- 동일 이름 비교 (안정 정렬)

#### `processContents(metadata)` - 우선순위: 중간

pCloud API 응답에서 폴더와 이미지를 분류/정렬한다.

```javascript
// 테스트 케이스 예시
processContents({
  metadata: {
    contents: [
      { name: 'ep2', isfolder: true },
      { name: 'ep1', isfolder: true },
      { name: 'cover.jpg', isfolder: false },
      { name: 'readme.txt', isfolder: false }
    ]
  }
});
// → { folders: [ep1, ep2], images: [cover.jpg] }
```

- 폴더/파일 분류 정확성
- 이미지 필터링 (비이미지 파일 제외)
- 자연 정렬 적용 확인
- 빈 contents, `metadata` 누락 등 방어 코드 검증

#### `getFileLink(code, fileid)` - 우선순위: 낮음

단순 URL 생성 함수.

```javascript
getFileLink('ABC', 12345)
// → 'https://api.pcloud.com/getpublinkdownload?code=ABC&fileid=12345'
```

#### 비동기 함수 (모킹 필요)

| 함수 | 역할 | 모킹 대상 |
|------|------|-----------|
| `fetchPublicLink(code)` | pCloud 공유 링크 메타데이터 조회 | `fetch` |
| `getImageUrl(code, fileid)` | 이미지 다운로드 URL 생성 (`hosts[0]` + `path` 조합) | `fetch` |

- 정상 응답 처리
- `data.error` 존재 시 예외 발생 확인
- 네트워크 오류 처리
- `getImageUrl`: `referrerPolicy: 'no-referrer'` 옵션 적용 확인

### 2.2 스토어 테스트 대상

#### `src/lib/stores/theme.js` - 우선순위: 중간

Svelte writable 스토어를 커스텀 래핑한 테마 스토어.

| 메서드 | 테스트 내용 |
|--------|-------------|
| `init()` | localStorage 저장값 우선 적용, 없으면 시스템 다크모드 감지 (`matchMedia`) |
| `toggle()` | `''` ↔ `'dark'` 토글, localStorage 동기화 |
| `set(value)` | 값 설정 + localStorage 동기화 |

- `localStorage` 모킹 필요
- `window.matchMedia` 모킹 필요
- SSR 환경 (`typeof window === 'undefined'`) 방어 코드 검증

### 2.3 컴포넌트 테스트 대상

Svelte 5 runes (`$state`, `$props`) 기반 컴포넌트 5개.

#### `LinkInput.svelte` - 우선순위: 높음

- 빈 입력값 제출 방지 (`inputValue.trim()` 검증)
- 로딩 중 입력/버튼 비활성화 (`disabled` 속성)
- 에러 메시지 표시 (`error` 상태)
- `onSubmit` 콜백 호출 확인
- 폼 제출 이벤트 처리 (`e.preventDefault()`)

#### `EpisodeList.svelte` - 우선순위: 중간

- 폴더 목록 렌더링
- 빈 목록일 때 "No folders found" 메시지 표시
- 폴더 클릭 시 `onSelect` 콜백 호출

#### `Header.svelte` - 우선순위: 중간

- 제목 텍스트 렌더링 (기본값: `'pCloud Comics'`)
- `showBack` prop에 따른 뒤로가기 버튼 표시/숨김
- 뒤로가기 버튼 클릭 시 `onBack` 콜백 호출
- `ThemeToggle` 컴포넌트 포함 확인

#### `ThemeToggle.svelte` - 우선순위: 낮음

- 테마 상태에 따른 아이콘 전환 (해/달 SVG)
- 클릭 시 `theme.toggle()` 호출

#### `ImageViewer.svelte` - 우선순위: 낮음 (통합 테스트 권장)

- 복잡한 비동기 로직 (`Promise.all`로 이미지 URL 일괄 로드)
- `localStorage` 기반 스크롤 위치 북마크 (`bookmark_${code}_${folderId}` 키)
- 로딩 진행률 표시 (`loadedCount / imageUrls.length`)
- `onMount` 2회 호출 구조 (이미지 로딩 + `beforeunload` 이벤트)
- 컴포넌트 단위 테스트보다 E2E가 적합

### 2.4 페이지 로직 테스트 대상

#### `+page.svelte` 네비게이션 상태 관리 - 우선순위: 높음

`+page.svelte`에 앱의 핵심 상태 관리 로직이 집중되어 있다. 3가지 뷰 상태(`input`, `list`, `viewer`)를 전환하는 상태 머신이다.

| 로직 | 테스트 내용 |
|------|-------------|
| `handleLinkSubmit(url)` | URL 제출 → `extractCode` → `fetchPublicLink` → 이미지만 있으면 `viewer`, 폴더 있으면 `list` |
| `handleFolderSelect(folder)` | 폴더 선택 → breadcrumb 추가 → 이미지 있으면 `viewer`, 폴더만 있으면 `list` |
| `handleBack()` | breadcrumb 기반 히스토리 되돌리기, 최상위에서 전체 상태 초기화 → `input` |
| `getCurrentTitle()` | breadcrumb 비어있으면 `'PclToon'`, 아니면 마지막 항목 이름 |

현재 이 로직이 컴포넌트에 직접 포함되어 있어 단위 테스트가 어렵다.

### 2.5 E2E 테스트 대상

| 시나리오 | 설명 |
|----------|------|
| 링크 입력 → 에피소드 목록 표시 | 메인 사용자 플로우 |
| 에피소드 선택 → 이미지 뷰어 표시 | 폴더 탐색 |
| 뒤로가기 네비게이션 | breadcrumb 기반 히스토리 (다단계) |
| 다크모드 토글 | 테마 전환 + localStorage 유지 |
| 스크롤 위치 북마크 | 뷰어 재진입 시 위치 복원 |
| 잘못된 링크 입력 | API 에러 → 에러 메시지 표시 |

E2E 테스트는 pCloud API 모킹이 필수이며, `ssr: false` (SPA 모드) 특성을 고려해야 한다.

## 4. 우선순위

단계별 도입 로드맵:

### Phase 1: 순수 함수 단위 테스트 (최소 노력, 최대 효과)

**대상**: `src/lib/pcloud.js`의 `extractCode`, `isImageFile`, `naturalSort`, `processContents`, `getFileLink`

- 외부 의존성 없는 순수 함수로 모킹 불필요
- Vitest 설치 + 테스트 파일 1개로 시작 가능
- 예상 소요 시간: 설정 30분 + 작성 1시간

### Phase 2: 스토어 + 비동기 함수 테스트

**대상**: `theme.js` 스토어, `fetchPublicLink`, `getImageUrl`

- `localStorage`, `window.matchMedia`, `fetch` 모킹 필요
- Phase 1 인프라 위에 추가

### Phase 3: 컴포넌트 테스트

**대상**: `LinkInput`, `EpisodeList`, `Header`

- `@testing-library/svelte` 추가 필요
- 사용자 인터랙션 + DOM 검증
- `+page.svelte`의 상태 관리 로직을 별도 모듈로 추출하면 테스트 용이

### Phase 4: E2E 테스트 (선택)

**대상**: 전체 사용자 플로우

- Playwright 도입 + pCloud API 모킹 서버 구성 필요
- SPA 모드(`ssr: false`) 특성 고려
- 프로젝트 규모 대비 비용이 크므로 선택적 도입

### 핵심 지표 목표

| 지표 | Phase 1 | Phase 2 | Phase 3 | Phase 4 |
|------|---------|---------|---------|---------|
| 테스트 수 | ~15 | ~30 | ~50 | ~60 |
| 코드 커버리지 | `pcloud.js` 100% | 유틸+스토어 100% | 70%+ | 85%+ |
| CI 실행 시간 증가 | +5초 | +10초 | +15초 | +45초 |

## 5. 미비점 및 개선 제안

### 5.1 테스트 인프라 전면 부재

- **현상**: 테스트 프레임워크, 파일, CI 단계가 모두 없어 코드 변경 시 회귀를 감지할 수단이 전무하다.
- **제안**: Vitest를 도입하고 `package.json`에 `"test": "vitest run"` 스크립트를 추가한다. CI 파이프라인에 `npm test` 단계를 삽입하여 빌드 전 품질 게이트를 확보한다.

### 5.2 `+page.svelte` 내 로직 중복

- **현상**: `isImageFile()` 함수와 `naturalSort` 비교 로직이 `pcloud.js`에 export되어 있음에도, `+page.svelte` 내에 동일한 로직이 인라인으로 재정의되어 있다. `isImageFile`은 별도 함수로 선언되고, `naturalSort`는 `localeCompare` 호출이 4곳에서 반복된다.
- **제안**: `+page.svelte`에서 인라인 정의를 제거하고 `pcloud.js`의 `isImageFile`, `naturalSort`, `processContents`를 import하여 사용한다. 이렇게 하면 단위 테스트 하나로 모든 사용처를 커버할 수 있고, 동작 불일치 위험을 제거한다.

### 5.3 상태 머신 로직의 테스트 어려움

- **현상**: `+page.svelte`의 뷰 전환 로직(`currentView`, `breadcrumb`, `handleBack`, `handleLinkSubmit`, `handleFolderSelect`)이 컴포넌트에 직접 결합되어 있어, UI 없이 상태 전환만 단독 테스트하기 어렵다.
- **제안**: 상태 머신 로직을 별도 모듈(`src/lib/navigation.js` 등)로 추출하면 순수 함수 수준의 단위 테스트가 가능해진다.

### 5.4 `ImageViewer`의 `onMount` 이중 등록

- **현상**: `ImageViewer.svelte`에서 `onMount`가 두 번 호출된다. 첫 번째는 이미지 URL 로딩과 저장된 스크롤 위치 복원용, 두 번째는 `beforeunload` 이벤트 리스너 등록용이다. 테스트 시 생명주기 시뮬레이션이 복잡해진다.
- **제안**: 하나의 `onMount`로 통합하여 테스트 예측 가능성을 높인다.

### 5.5 타입 안전성 부재

- **현상**: TypeScript가 아닌 순수 JavaScript를 사용하고 있어, pCloud API 응답 구조(`data.metadata.contents`, `data.hosts[0]`, `data.path`)에 대한 타입 검증이 없다.
- **제안**: JSDoc 타입 어노테이션 또는 TypeScript 전환으로 API 응답 형상을 명시하면, 테스트 fixture 작성 시 정확한 데이터 구조를 참조할 수 있다.

### 5.6 에러 처리 테스트 불가 영역

- **현상**: `ImageViewer.svelte`에서 이미지 URL 로딩 실패 시 `catch` 블록이 `null`을 반환하고 `filter(Boolean)`으로 제거하는데, 사용자에게 부분 로딩 실패를 알리는 UI가 없다.
- **제안**: 부분 실패 시 사용자 알림 UI를 추가하고, 해당 동작을 컴포넌트 테스트로 검증한다.
